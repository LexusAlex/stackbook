# Git и сервисы размещения репозиториев

Вы сделали коммит, а коллега говорит: «Я не вижу изменений». Почему так происходит, если Git уже сохранил результат?

**Коммит записывает состояние в конкретный репозиторий. Чтобы другой участник получил этот результат, историю нужно передать между репозиториями.** GitHub и GitLab предоставляют место для хранения репозиториев и инструменты совместной работы.

Отведите **25–35 минут** на объяснения и практику. Из [первого урока](./why-version-control) понадобятся понятия рабочего файла, коммита и репозитория. Нужны браузер и заметка для ответов; устанавливать Git или создавать учётную запись пока не требуется.

После урока вы сможете:

- различать Git, серверный репозиторий и сайт для работы с ним;
- объяснить, где находится новый коммит до и после отправки;
- отличить получение истории от обновления рабочих файлов;
- найти файлы и коммиты в публичном репозитории GitHub.

## 1. Git, GitHub и GitLab выполняют разные задачи

**Git** — система контроля версий. Она записывает коммиты, хранит историю и позволяет сравнивать версии. Локальный репозиторий находится на вашем компьютере: уже имеющаяся история и создание новых коммитов доступны без интернета.

**Хостинг репозиториев** — место, где размещают репозитории для доступа по сети. В этом уроке сервером будем называть компьютер, к которому участники обращаются для обмена историей.

**GitHub** и **GitLab** — платформы для размещения Git-репозиториев. Кроме хранения истории, они предоставляют веб-интерфейс: страницы файлов, обсуждения и инструменты проверки предложенных изменений.

| Что | За что отвечает | Пример |
| --- | --- | --- |
| Git | Запись и обработка истории версий | Создать коммит в локальном репозитории |
| Репозиторий на сервере | Хранение переданной туда истории | Получить коммиты от одного участника и отдать другому |
| Веб-интерфейс GitHub или GitLab | Просмотр проекта и совместная работа в браузере | Открыть изменение, прочитать обсуждение |

Git не привязан к одному сервису: размещение на GitHub — один из вариантов. В GitLab репозиторий входит в состав **проекта**, который также содержит настройки и другие инструменты. Эти роли описаны в [GitHub Docs: About Git](https://docs.github.com/en/get-started/using-git/about-git) и [GitLab Docs: Repository](https://docs.gitlab.com/user/project/repository/).

## 2. Локальный репозиторий, удалённый репозиторий и страница в браузере

Представьте сайт Анны из первого урока. Теперь над ним помогают работать два человека — Анна и Борис. У каждого своя рабочая папка и свой локальный репозиторий.

Для обмена они используют репозиторий на сервере:

```text
Компьютер Анны  ←→  Репозиторий на сервере  ←→  Компьютер Бориса
```

По отношению к Анне серверный репозиторий называют **удалённым**. По-английски вы встретите слово **remote**. Строго говоря, удалённый репозиторий может находиться и в другой папке того же компьютера; здесь рассматриваем привычный вариант с сервером. Это уточнение есть в [Pro Git: работа с удалёнными репозиториями](https://git-scm.com/book/en/v2/Git-Basics-Working-with-Remotes).

Открытая страница GitHub показывает данные, доступные **на стороне сервиса**. Она не читает рабочую папку Анны с её компьютера. Обновление страницы в браузере также не обновляет локальный репозиторий Бориса.

Полезно каждый раз уточнять место действия:

| Действие | Где искать результат |
| --- | --- |
| Анна сохранила текст в редакторе | В её рабочем файле |
| Анна создала локальный коммит | В её локальной истории |
| Анна успешно отправила коммит в серверный репозиторий | В истории выбранной ветки на сервере |
| Борис открыл страницу проекта в браузере | Он видит серверный вариант; его локальные файлы от этого не меняются |

**Ветка** — отдельная линия развития проекта. Для примеров ниже считаем, что все работают с одной веткой `main`, а независимых изменений у Бориса нет. Название `main` выбрано для нашего примера; в другом репозитории оно может отличаться.

## 3. Проследите путь одного коммита

В начале у Анны, Бориса и сервера есть одинаковая история: `A → B`. Буквы — условные метки коммитов. Под «состоянием ветки» в таблице понимаем её последний коммит вместе с предшествующей историей.

Анна добавляет контакты и сохраняет их коммитом C. Затем передаёт C на сервер. Позже Борис получает новую историю и применяет её к своей работе.

| Шаг | Ветка у Анны | Ветка на сервере | Ветка и рабочие файлы у Бориса |
| --- | --- | --- | --- |
| 1. Исходное состояние | `A → B` | `A → B` | `A → B`, файлы из B |
| 2. Анна создала C локально | `A → B → C` | `A → B` | `A → B`, файлы из B |
| 3. Анна успешно отправила C | `A → B → C` | `A → B → C` | `A → B`, файлы из B |
| 4. Борис получил историю и обновил свою ветку до C | `A → B → C` | `A → B → C` | `A → B → C`, файлы из C |

После шага 2 коммит уже существует, но только у Анны. После шага 3 его можно увидеть на сервере, однако рабочие файлы Бориса ещё прежние. Только после шага 4 Борис работает с новым состоянием.

В примере отправка успешна. В реальной работе сервер может отклонить её, например из-за недостаточных прав. Поэтому важен результат действия: сама попытка отправки не доказывает, что сервер получил нужный коммит.

### Почему отправка не включает все файлы компьютера

После C Анна ещё раз изменила приветствие и сохранила рабочий файл, но не включила эту правку в новый коммит. Отправка C передаст историю с C. Более поздний текст, оставшийся только в рабочем файле, в этот коммит не входит.

Различайте четыре результата: **сохранённый рабочий файл → локальный коммит → коммит на сервере → обновлённая работа другого участника**.

## 4. Клонирование, отправка и получение

В описаниях Git встречаются четыре названия действий. Пока достаточно понимать их назначение; выполнять команды не нужно.

| Название | Смысл | Что важно различать |
| --- | --- | --- |
| Клонирование — clone | Создать локальный репозиторий на основе существующего | Это первый шаг получения своей рабочей копии с историей |
| Отправка — push | Передать локальные коммиты и обновить выбранную ветку на сервере | Рабочие правки без коммитов сами по себе не отправляются |
| Получение — fetch | Скачать доступные новые данные и обновить сведения об удалённых ветках | Текущая локальная ветка и рабочие файлы автоматически не обновляются |
| Получение с интеграцией — pull | Получить изменения и включить их в текущую ветку | При собственных изменениях может понадобиться разрешить конфликт |

**Конфликт** возникает, когда изменения не удаётся совместить автоматически и человеку нужно выбрать итоговый вариант. В нашей таблице у Бориса нет независимых правок, поэтому рассматриваем простое успешное обновление.

После одного лишь fetch данные C могут уже быть в локальном репозитории Бориса, а его текущая ветка и рабочие файлы — всё ещё соответствовать B. Поэтому фразы «получил новые коммиты» и «обновил рабочие файлы» описывают разные результаты. Это различие разобрано в [Pro Git: получение и отправка изменений](https://git-scm.com/book/en/v2/Git-Basics-Working-with-Remotes).

### Почему Download ZIP не заменяет клонирование

На GitHub можно скачать исходники кнопкой **Download ZIP**. Архив содержит файлы выбранного состояния, но не всю историю репозитория. Обычное клонирование создаёт локальный Git-репозиторий с историей; у клонирования также бывают специальные режимы, ограничивающие загружаемые данные.

Для чтения файлов архив может быть достаточен. Для изучения истории и обмена коммитами нужна локальная копия репозитория. Различие подтверждают [документация архивов GitHub](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives) и [руководство git clone](https://git-scm.com/docs/git-clone).

## 5. Что показывает страница репозитория

Веб-интерфейс позволяет просматривать файлы и историю без локальной установки Git. Для знакомства будем использовать GitHub; в GitLab есть похожие возможности с другими названиями и расположением элементов.

На странице GitHub полезно узнавать следующие элементы:

| Элемент | Что показывает |
| --- | --- |
| Владелец и имя репозитория | Какой проект открыт, например `git/git` |
| Выбранная ветка | Состояние какой линии развития вы просматриваете |
| Code и список файлов | Файлы выбранной ветки или другого выбранного состояния |
| README | Описание проекта, если такой файл есть |
| Commits / история | Сообщения коммитов и переход к их содержимому |
| Pull requests | Предложения изменений, которые можно обсудить и проверить |

**Pull request** — предложение включить изменения из одной ветки в другую. В GitLab похожий инструмент называется [**merge request**](https://docs.gitlab.com/user/project/merge_requests/). Это средства совместной работы платформы. Создание локального коммита само по себе не создаёт такое предложение.

Сервисы также позволяют редактировать файлы в браузере. Если вы создали коммит через веб-редактор своего репозитория, он появляется на стороне сервиса. Локальная копия на компьютере от этого сама не обновляется. Процесс показан в [GitHub Docs: редактирование файлов](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files).

## 6. «На сервере», «публично» и «сайт работает»

**Публичный репозиторий** доступен для просмотра всем в интернете. **Приватный репозиторий** доступен тем, кому предоставлены соответствующие права. Возможность прочитать публичный проект не даёт любому посетителю права изменять его. Видимость и разрешения описаны в [GitHub Docs: о репозиториях](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories).

Поэтому слово «опубликовать» нужно уточнять. В контексте обмена коммитами мы говорим об **отправке истории в выбранный репозиторий**. Доступ к этой истории зависит от его настроек.

Если проект — веб-сайт, размещение исходников на GitHub также не означает, что сайт уже собран и доступен посетителям. Для этого нужен отдельный процесс развёртывания. Его можно настроить автоматически после отправки, но одной отправки коммитов без такой настройки недостаточно. Один из вариантов для статического сайта — [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

## 7. Практика: определите, где находится новая версия

Анна и Борис уже работают с состоянием C. На сервере тоже есть `A → B → C`. Владелец проекта через веб-редактор этого серверного репозитория создаёт D — исправление описания. После этого участники ничего не получают с сервера.

Ответьте в заметке до открытия разбора:

1. Где сейчас есть D: на сервере, у Анны или у Бориса?
2. Изменятся ли локальные файлы Бориса, если он просто прочитает D в браузере?
3. После одного лишь fetch у Бориса есть данные D. Что ещё нужно, чтобы работать с файлами из D?
4. Нужно ли Анне повторно создавать такой же коммит D, чтобы получить исправление?

::: details Разбор задания

1. D есть на сервере. Обе локальные ветки пока остаются на C.
2. Нет. Просмотр страницы не обновляет локальные файлы.
3. Нужно включить полученное изменение в свою текущую ветку. В нашем простом случае без независимых правок — обновить её с C до D; тогда рабочие файлы будут соответствовать D.
4. Нет. Анне нужно получить существующую историю и обновить свою работу. Это тот же коммит D, который уже создан на сервере.

Проверочный результат: вы различаете место хранения данных, положение текущей ветки и содержимое рабочих файлов.

:::

## 8. Практика: прочитайте публичный репозиторий

Откройте [репозиторий Git на GitHub — git/git](https://github.com/git/git). Это публичное зеркало исходного кода самого Git. В упражнении достаточно просмотра страниц; клонировать проект, скачивать архив или менять файлы не нужно.

1. Найдите имя владельца и репозитория: в данном случае оба — `git`.
2. Найдите пометку **Public** и имя выбранной ветки. Запишите фактическое имя: оно не обязано быть `main`.
3. В разделе **Code** найдите `README.md` в списке файлов и откройте его. Достаточно увидеть, что это содержимое файла из проекта; понимать исходный код не требуется.
4. Вернитесь к основной странице репозитория. Откройте ссылку на историю коммитов возле последнего изменения: она может содержать слово **Commits**, число коммитов или значок истории.
5. Откройте коммит, в котором есть изменения файлов. Найдите его сообщение, идентификатор и перечень изменённых файлов.

На узком экране часть элементов находится в дополнительных меню. Если ссылка на историю не видна, используйте [прямой переход к истории git/git](https://github.com/git/git/commits). Сообщения и количество коммитов со временем меняются; запишите те данные, которые видите сейчас.

Заполните короткую карточку:

```text
Сервис:
Владелец / репозиторий:
Видимость:
Выбранная ветка:
Открытый файл:
Сообщение одного коммита и его идентификатор:
Чью историю показывает браузер:
Создался ли от просмотра локальный репозиторий на моём компьютере:
```

::: details Как проверить карточку

- **Сервис:** GitHub.
- **Владелец / репозиторий:** `git/git`.
- **Видимость:** Public.
- **Ветка:** совпадает с выбранной в интерфейсе.
- **Файл:** `README.md`.
- **Коммит:** записанные сообщение и идентификатор относятся к одной открытой записи.
- **История в браузере:** история репозитория, размещённого на GitHub.
- **Локальный репозиторий:** от одного просмотра страницы не создаётся.

Упражнение выполнено, если вы нашли конкретный файл и коммит и можете объяснить, где хранятся просмотренные данные.

:::
