# Зачем нужен контроль версий

Вы изменили текст на сайте, добавили контакты и заметили, что старое приветствие было лучше. Как вернуть его, сохранив новые контакты? А если вы уже не помните прежний текст?

**Git помогает хранить историю проекта, сравнивать сохранённые версии и возвращаться к нужному содержимому.** В этом уроке разберём, как такая история устроена и какую пользу она приносит даже при работе в одиночку.

Отведите **25–35 минут** на чтение и задания. Нужны браузер и заметка для ответов; устанавливать Git и выполнять команды пока не требуется.

После урока вы сможете:

- объяснить разницу между текущими файлами проекта и его историей;
- различать снимок, коммит и репозиторий;
- по примеру найти изменение с ошибкой и предложить исправление;
- выбрать понятные результаты, которые стоит сохранять отдельными коммитами.

## 1. Почему обычного сохранения файла бывает мало

Представьте, что вы делаете сайт-визитку. В понедельник написали приветствие, во вторник его улучшили, а в среду добавили контакты. После очередного редактирования заметили опечатку.

Кнопка **«Сохранить»** записывает текущий текст файла на диск. Если у вас остался только этот файл, по нему трудно узнать, какие варианты были раньше и почему вы их меняли.

Один из привычных способов подстраховаться — делать копии:

```text
site/
site-copy/
site-final/
site-final-fixed/
```

Сначала это помогает. Но постепенно возникают вопросы: где действительно последняя версия, в какой папке есть новые контакты и какой именно текст изменился между двумя копиями? Название `final` этих сведений не даёт.

**Контроль версий** позволяет сохранять выбранные состояния файлов и затем обращаться к ним. Git — программа для такого контроля версий. Она помогает ответить на вопросы «что изменилось?», «когда?» и «кем записано изменение?». Понятное сообщение к изменению помогает объяснить и его причину. Возможности сравнения и восстановления описаны в [Pro Git: о контроле версий](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control).

История полезна и одному человеку: через неделю вы можете забыть собственное решение. В команде она также помогает разобраться в работе другого участника.

## 2. Из чего состоит история проекта

Сначала разберём четыре слова, которые будут встречаться во всём курсе.

### Рабочие файлы

Это файлы, которые вы сейчас открываете и редактируете: например, текст главной страницы и описание сайта. Их текущее содержимое может отличаться от последнего сохранённого в истории состояния.

Папку с такими файлами называют **рабочим каталогом**. Представьте её как стол, на котором лежит текущая работа.

### Снимок

**Снимок** описывает состояние файлов, включённых в версию проекта. Он позволяет узнать, какое содержимое было у каждого из этих файлов в выбранный момент.

Например, в снимке есть правильное приветствие и описание без контактов. Позже рабочие файлы могут измениться, а сохранённый снимок по-прежнему будет описывать прежний вариант.

### Коммит

**Коммит** — запись в истории, которая ссылается на снимок проекта. У неё есть идентификатор, сведения об авторе и времени, сообщение, а также связь с предыдущей историей. Первый коммит начинает историю; в нашем простом примере каждый следующий продолжает предыдущий.

Сообщение вроде «Добавить контакты» объясняет смысл сохранённого результата. Идентификатор позволяет указать конкретный коммит, даже если сообщения двух записей совпадают.

### Репозиторий

**Репозиторий** хранит снимки, коммиты и другие служебные данные Git. В обычном локальном проекте эти данные находятся в скрытом каталоге `.git`, рядом с рабочими файлами:

```text
site/
├── .git/       ← история и служебные данные Git
├── README.md   ← рабочий файл с описанием сайта
└── home.md     ← рабочий файл с текстом главной
```

`README.md` и `home.md` здесь — обычные текстовые файлы. Расширение `.md` означает Markdown; для примера достаточно читать их как текст.

Связь понятий такая: **вы редактируете рабочие файлы, выбираете состояние для сохранения и создаёте коммит; репозиторий хранит эту историю**. Модель снимков и устройство рабочего каталога описаны в [Pro Git: что такое Git](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F).

## 3. Прочитайте историю двух файлов

Будем считать, что оба файла уже отслеживаются: Git знает о них, а их содержимое включается в сохраняемые версии. Каждое описанное ниже состояние явно сохранено коммитом. **A, B и C — условные обозначения для урока**, а не настоящие идентификаторы Git.

### Коммит A: создать основу сайта

В `README.md` записано:

```text
Сайт Анны. Здесь я рассказываю о своих проектах.
```

В `home.md` записано:

```text
Привет!
```

Мы сохранили первый результат — основу сайта. У нас появилась точка, с которой можно сравнивать дальнейшую работу.

### Коммит B: уточнить приветствие

В `home.md` заменили текст на `Добро пожаловать!`. Описание в `README.md` оставили прежним и сохранили результат коммитом B.

**Снимок B описывает оба файла**, хотя менялся только один. В нём есть новое приветствие и прежнее описание. Неизменившийся файл продолжает входить в состояние проекта; на уровне модели Git повторно использует уже сохранённое содержимое.

### Коммит C: добавить контакты и изменить приветствие

В `README.md` дописали строку `Связь: anna@example.com`. Одновременно в `home.md` случайно переставили буквы: получилось `Добро пожаловтаь!`. Затем обе правки включили в коммит C.

Сведём историю в таблицу:

| Коммит и сообщение | README.md | home.md |
| --- | --- | --- |
| A — «Создать основу сайта» | Описание сайта | `Привет!` |
| B — «Уточнить приветствие» | Прежнее описание сайта | `Добро пожаловать!` |
| C — «Добавить контакты и изменить приветствие» | Описание сайта и контакты | `Добро пожаловтаь!` |

Каждая строка показывает целое состояние двух файлов. Читать историю можно по порядку: сначала появилась основа, затем улучшилось приветствие, потом добавились контакты и возникла ошибка.

## 4. Найдите ошибку и сохраните полезную работу

Допустим, сейчас рабочие файлы соответствуют C. Вы видите опечатку, но хотите оставить добавленные контакты.

Для начала **сравним B и C**. В сравнении, которое называют **diff**, видны различия между выбранными состояниями. Ниже упрощённый пример: строка с `-` была в B, строка с `+` появилась в C. Эти строки показывают изменения, выполнять их как команды не нужно.

```diff
 README.md
 Сайт Анны. Здесь я рассказываю о своих проектах.
+Связь: anna@example.com

 home.md
-Добро пожаловать!
+Добро пожаловтаь!
```

Теперь понятно, что произошло:

1. В `README.md` добавили нужные контакты.
2. В `home.md` правильное приветствие заменили текстом с опечаткой.
3. Для исправления нужно поменять приветствие и сохранить контакты.

Если вернуть **весь проект** к состоянию B, в рабочих файлах исчезнут и новые контакты. Такой результат не соответствует задаче.

Подходящее исправление — взять правильный текст `home.md` из B, оставив `README.md` из C. В этом примере можно и просто исправить опечатку вручную: важно получить нужное содержимое обоих файлов. Затем сохраним результат новым коммитом D — «Исправить опечатку в приветствии».

```text
A → B → C → D
            ↑
     новое исправление
```

В снимке D приветствие правильное, контакты на месте. В истории остаются C с ошибкой и D с её исправлением. Чтобы исправить текущие файлы таким способом, удалять прежний коммит не требуется.

## 5. Сохранить, подготовить, сделать коммит

В Git полезно различать три действия. Здесь разберём их смысл без команд:

| Действие | Что получается |
| --- | --- |
| Сохранить файл в редакторе | Новое содержимое записано в рабочий файл на диске |
| Подготовить изменения | Выбрано содержимое для следующего коммита; эта подготовленная область называется индексом |
| Создать коммит | Подготовленное состояние записано в локальную историю |

Представьте, что после B вы трижды меняли приветствие и каждый раз нажимали «Сохранить». **Три сохранения в редакторе сами по себе не создают три коммита.** В рабочем файле будет последний сохранённый вариант, а B по-прежнему будет описывать прежнее состояние.

Подготовка нужна, чтобы управлять содержимым будущего коммита. Например, можно подготовить добавление контактов, а незаконченный текст главной оставить для другой задачи. В снимок войдёт выбранное состояние, поэтому перед коммитом полезно проверить подготовленные изменения. Этот цикл описан в [Pro Git: запись изменений в репозиторий](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository).

### Как выбрать момент для коммита

Хороший ориентир — небольшой результат, который можно объяснить одной фразой и проверить. Например: «Добавить контакты», «Исправить опечатку», «Уточнить описание проекта».

В нашем C были смешаны две правки. Если бы добавление контактов и изменение приветствия сохранили отдельно, разбираться в истории было бы проще. Сообщение описывало бы одну задачу, и её результат было бы легче оценить.

| Сообщение | Что читатель узнаёт из истории |
| --- | --- |
| «Изменения» | Для понимания результата придётся изучить содержимое |
| «Добавить адрес для связи» | В проекте появились контактные данные |
| «Исправить опечатку в приветствии» | Изменение исправляет текст главной страницы |

Количество коммитов само по себе не делает историю полезной. Важно, чтобы сохранённые шаги имели понятный смысл.

## 6. Где находится история и при чём здесь GitHub

**Локальный** означает «на вашем компьютере». Создать коммит, просмотреть уже имеющуюся историю и сравнить локальные версии можно без интернета.

Для обмена результатами используют другой репозиторий, например размещённый на сервере. **GitHub** — сервис, на котором можно хранить Git-репозитории и обсуждать работу над проектом. Git создаёт и обрабатывает историю, а GitHub предоставляет место для её размещения и инструменты совместной работы. Это различие объясняется в [GitHub Docs: About Git](https://docs.github.com/en/get-started/using-git/about-git).

Представьте, что на сервере пока есть A и B, а вы создали C:

```text
Ваш компьютер:       A → B → C
Репозиторий сервера: A → B
```

Создание локального C само по себе не передаёт его на сервер. После отдельной успешной отправки нужной истории на обеих сторонах могут быть A, B и C. Чтобы получить эту историю у себя, другому участнику тоже нужно обратиться к серверу.

Поэтому полезно задавать два разных вопроса: «Я сохранил результат в своей истории?» и «Я передал его туда, откуда его получат остальные?»

## 7. Чего не стоит ожидать от Git

История помогает, когда вы понимаете, какое состояние действительно сохранили. Разберём три частых ожидания.

**«Git автоматически запомнит каждый мой вариант».** В обычном процессе историю записывают коммитами. Если вы несколько раз переписали рабочий файл без коммитов, Git не обещает восстановить каждый промежуточный текст. У редактора может быть собственная история, но это отдельный механизм.

**«Любой новый файл уже есть в истории».** Самого появления файла в папке недостаточно. Новый файл нужно включить в отслеживание и записать его содержимое коммитом. В нашем примере мы заранее договорились, что оба файла уже отслеживаются.

**«Если есть коммит, содержимое точно правильное».** Коммит C показывает обратное: Git сохранил и полезные контакты, и опечатку. Правильность результата проверяет человек или отдельные проверки проекта.

История только на одном диске также может быть потеряна вместе с ним. Для сохранности нужны отдельные копии; отправка коммитов в другой репозиторий сохраняет там переданную историю, но не копирует автоматически все ваши локальные файлы и незакоммиченные правки.

## 8. Практика: объясните исправление

Вернитесь к таблице A, B и C и сначала ответьте в заметке, не открывая разбор:

1. Между какими двумя коммитами появилась опечатка?
2. Почему полное восстановление состояния B не решает нашу задачу?
3. Что должно находиться в каждом из двух файлов после исправления?
4. Какое сообщение вы дадите новому коммиту D?

::: details Разбор задания

1. Опечатка появилась между B и C: в B приветствие правильное, в C буквы переставлены.
2. В B ещё нет контактов. Полное восстановление этого состояния уберёт их из рабочих файлов вместе с опечаткой.
3. В `home.md` должно быть `Добро пожаловать!`, в `README.md` — описание сайта и строка `Связь: anna@example.com`.
4. Подойдёт «Исправить опечатку в приветствии». Сообщение объясняет результат, который отличает D от C.

Правильный ответ сохраняет обе нужные части: исправленное приветствие и актуальные контакты. Формулировки могут отличаться от приведённых.

:::

## 9. Практика: спланируйте историю своего проекта

Выберите знакомый небольшой проект: сайт, учебную программу или набор заметок. Для него придумайте два последовательных результата и одну возможную ошибку.

Заполните шаблон:

```text
Мой проект:
Какие файлы в нём будут:
Первый законченный результат и сообщение коммита:
Следующий отдельный результат и сообщение коммита:
Какую ошибку я могу допустить:
С какой прежней версией я сравню файл:
Какие полезные изменения нужно оставить при исправлении:
```

::: details Пример заполнения

- **Проект:** заметки по изучению английского.
- **Файлы:** `words.md` со словами и `schedule.md` с расписанием занятий.
- **Первый результат:** добавить пять слов с переводом; сообщение «Добавить первые пять слов».
- **Следующий результат:** составить расписание; сообщение «Добавить расписание занятий».
- **Ошибка:** при дальнейшем редактировании записать неправильный перевод одного слова.
- **Сравнение:** сопоставить текущий `words.md` со снимком, в котором перевод был правильным.
- **Что сохранить:** новое расписание из `schedule.md` и остальные правильные слова.

Здесь история нужна для конкретной задачи: исправить перевод, сохранив другую полезную работу.

:::

Проверьте себя: по каждому сообщению понятно, что сделано; два результата относятся к отдельным задачам; при исправлении назван конкретный файл и указано, что нужно сохранить.
