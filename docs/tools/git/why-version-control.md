# Зачем нужен контроль версий

**За 10–15 минут разберёте историю небольшого проекта, выберете способ исправить ошибку и проверите понимание прямо на странице.**

Для урока нужны браузер и заметка для самостоятельного задания. Разберём идею контроля версий на готовом примере; команды для создания репозитория и коммитов будут отдельными темами.

## 1. Какую проблему решаем

Представьте, что вы делаете небольшой сайт. Сначала написали приветствие, потом изменили заголовок и добавили контакты. Позже заметили опечатку.

В текущих файлах видно, что находится на сайте сейчас. Для исправления хочется узнать:

- какой текст был раньше;
- в каком изменении появилась опечатка;
- как вернуть удачный заголовок, сохранив новые контакты.

**Контроль версий** сохраняет историю состояний файлов, чтобы их можно было сравнивать и восстанавливать. Git — система контроля версий, которую мы будем изучать. Такую историю можно вести для кода, документации и других файлов проекта. [Объяснение в Pro Git](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control).

## 2. Три понятия: снимок, коммит, репозиторий

| Понятие | Что означает |
| --- | --- |
| Снимок | Сохранённое состояние отслеживаемых файлов проекта |
| Коммит | Запись в истории, связанная со снимком: у неё есть идентификатор, автор и сообщение |
| Репозиторий | Хранилище истории и служебных данных проекта |

**Коммит фиксирует подготовленное состояние проекта.** Вы выбираете, какие изменения включить в это состояние, и сохраняете его в историю. Файлы, которые не менялись, продолжают входить в снимок в прежнем виде. [Модель снимков в Pro Git](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F).

Сообщение помогает понять смысл изменения. Например, «Добавить контакты на главную» полезнее, чем «Изменить файлы»: понятно, какой результат хотели получить.

## 3. Разберите историю двух файлов

В учебном проекте два файла:

```text
README.md — описание сайта и контакты
home.md   — текст главной страницы
```

Оба файла отслеживаются. Предположим, их состояния явно сохранили тремя коммитами. **A, B и C — условные обозначения** для этого примера.

| Коммит и его смысл | README.md | home.md |
| --- | --- | --- |
| A — создать черновик | Краткое описание сайта | Привет |
| B — уточнить приветствие | Краткое описание сайта | Добро пожаловать |
| C — добавить контакты и изменить текст | Описание сайта и контакты | Добро пожаловтаь |

У снимка B есть состояние обоих файлов: новое приветствие и прежнее описание. В C появились контакты, а в приветствии возникла опечатка. Git сохранил и это состояние: наличие коммита само по себе не доказывает, что текст правильный.

Сравнив B и C, можно увидеть две разные правки. Задача — исправить приветствие и оставить контакты. Для этого подойдёт текст `home.md` из B, а `README.md` останется в состоянии C.

Полученный результат можно сохранить новым коммитом D — «Исправить приветствие». В истории останутся и исходное изменение, и его исправление. Способы восстановления файлов разберём в отдельных практических уроках.

## 4. Сохранение файла и коммит — разные действия

Когда вы нажимаете **«Сохранить»** в редакторе, меняется рабочий файл на диске. Чтобы подготовленная версия вошла в историю Git, создают коммит.

Допустим, после B вы изменили приветствие ещё три раза и каждый раз сохранили файл. Если новых коммитов не было, эти три промежуточных состояния не становятся тремя отдельными версиями в истории Git. В рабочем файле останется последнее сохранённое содержимое, а B будет по-прежнему описывать свой прежний снимок.

Поэтому полезно фиксировать понятные законченные результаты: создать основу страницы, добавить контакты, исправить ошибку. Подготовка изменений и создание коммита — явные шаги, описанные в [Pro Git](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository).

## 5. История начинается на вашем компьютере

Коммиты создаются в **локальном репозитории**. Сохранение коммита и просмотр уже имеющейся локальной истории доступны без подключения к интернету.

Отправка коммитов в другой репозиторий — отдельное действие. Оно позволяет обмениваться историей с другими участниками. Собственный локальный коммит ещё не означает, что коллега получил ваши изменения. [Локальные операции Git](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F).

## 6. Примените идею к своему проекту

Выберите небольшой знакомый проект: сайт, набор заметок или учебную программу. В заметке заполните четыре строки:

```text
Мой проект:
Какой первый законченный результат стоит сохранить:
Какое следующее изменение стоит сохранить отдельно:
Какой файл я хотел бы уметь сравнить с прежней версией:
```

Назовите конкретные результаты, например «Добавить раздел контактов». Слова «сохранить всё» не объясняют, что именно изменилось.

::: details Пример заполнения

- **Мой проект:** сайт-визитка.
- **Первый результат:** создать главную страницу с именем и кратким описанием.
- **Следующее изменение:** добавить контакты для связи.
- **Файл для сравнения:** текст главной страницы — посмотреть, какое приветствие было до редактирования.

Это один из возможных ответов. Для своего проекта достаточно выбрать осмысленные точки сохранения и объяснить, зачем понадобится история.

:::

## Результат урока

Урок пройден, если вы:

- различаете рабочий файл и состояние, сохранённое коммитом;
- можете по таблице выбрать прежний вариант одного файла, сохранив нужные изменения другого;
- понимаете, что локальный коммит и передача изменений другому участнику — отдельные действия;
- выбрали хотя бы две понятные точки сохранения для своего проекта.

Если ответ на вопрос не получился, откройте подсказку, вернитесь к примеру и затем попробуйте ответить ещё раз.
