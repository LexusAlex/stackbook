# Устройство конфигурации

Найдём главный файл Nginx и проследим, как он подключает настройки сайтов. Результат — вы можете назвать файл с нужным блоком `server`, объяснить его место в конфигурации и проверить, что Nginx его читает.

## Перед началом

Нужен сервер Ubuntu или Debian с установленным Nginx и доступом к `sudo`. Установка описана в статье [«Установка Nginx»](./installation), работа с пакетной службой — в [«Запуск и автозагрузка»](./startup).

Здесь достаточно изучить существующие файлы. Примеры ниже показывают их структуру; заменять ими пакетный `nginx.conf` не требуется.

## 1. Найдите главный файл

Посмотрите параметры сборки и команду запуска пакетной службы:

```sh
/usr/sbin/nginx -V 2>&1
systemctl cat nginx.service --no-pager
```

В выводе `-V` найдите `--conf-path`. Для рассматриваемых пакетов обычно указан `/etc/nginx/nginx.conf`. В unit-файле проверьте `ExecStart` и дополнения к нему: параметр `-c` выбирает другой главный файл, а `-p` меняет префикс путей. Если служба использует другой бинарный файл или параметры `-c`, `-p`, учитывайте их и в командах проверки. [Как определить путь к конфигурации](https://docs.nginx.com/nginx/admin-guide/basic-functionality/managing-configuration-files/#directives).

Для стандартного пути прочитайте файл:

```sh
sudo sed -n '1,200p' /etc/nginx/nginx.conf
```

Команда показывает первые 200 строк. Если файл длиннее, продолжите чтение, изменив диапазон. Путь, указанный в `--conf-path`, — значение по умолчанию при сборке; параметры службы могут его переопределять.

## 2. Разберите вложенность

Настройки записываются директивами. Простая директива заканчивается `;`, блок содержит директивы в фигурных скобках, а `#` начинает комментарий до конца строки. Контекст — область, в которой разрешён определённый набор директив. [Структура конфигурации Nginx](https://nginx.org/en/docs/beginners_guide.html#conf_structure).

Небольшой пример для чтения:

```nginx
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    server {
        listen 127.0.0.1:8080;
        server_name localhost;

        location / {
            return 200 "configuration example\n";
        }
    }
}
```

| Контекст | Где находится | За что отвечает в примере |
| --- | --- | --- |
| `main` | Вне блоков верхнего уровня | Общие параметры процессов: `worker_processes` |
| `events` | В `main`, рядом с `http` | Обработка соединений: `worker_connections` |
| `http` | В `main` | HTTP-настройки и блоки сайтов |
| `server` | В `http` | Виртуальный сервер с адресом, портом и именами |
| `location` | В `server` | Правила обработки URI запроса |

Слова `main` и фигурного блока `main {}` в файле нет: так называют внешний уровень. В этом примере путь к правилам запроса — `main → http → server → location`; блок `events` находится отдельно.

Допустимый контекст каждой директивы указан в поле `Context` её справки. Например, `listen` задаётся в HTTP-блоке `server`, а `location` нельзя просто вынести на уровень `http`. Не считайте наследование общим правилом для всех настроек: оно зависит от директивы. [Справка HTTP-модуля](https://nginx.org/en/docs/http/ngx_http_core_module.html), [наследование настроек](https://docs.nginx.com/nginx/admin-guide/basic-functionality/managing-configuration-files/#inheritance).

## 3. Проследите include

Директива `include` подключает отдельный файл или файлы по маске. Например, внутри существующего `http` может находиться:

```nginx
include /etc/nginx/conf.d/*.conf;
```

Подключённые здесь файлы читаются в контексте `http`. Поэтому файл сайта может содержать `server { ... }` без внешнего `http { ... }`. Повторная обёртка `http` приведёт к ошибке контекста. Если же `include` расположен внутри `server`, подключаемому фрагменту нужны директивы, допустимые на этом уровне. [Директива include](https://nginx.org/en/docs/ngx_core_module.html#include).

Для каждого подключения ответьте на три вопроса: где стоит `include`, какие пути подходят под него и какие блоки находятся в этих файлах. Название каталога само по себе не задаёт контекст.

Маска `*.conf` включает `example.conf`, но не `example.conf.disabled`. Резервная копия `example-backup.conf` тоже подходит под эту маску; храните такие копии вне подключаемого набора. Для прямого подключения одного файла проверьте, что он существует.

## 4. Учитывайте источник пакета

В статье об установке используется официальный репозиторий `nginx.org`. Его [пакетный nginx.conf](https://github.com/nginx/pkg-oss/blob/master/debian/debian/nginx.conf) подключает `/etc/nginx/conf.d/*.conf` внутри `http`. Пакеты Ubuntu/Debian могут использовать также схему `sites-available` и `sites-enabled`. [Описание Ubuntu](https://ubuntu.com/server/docs/how-to/web-services/configure-nginx/), [структура каталогов Debian](https://wiki.debian.org/Nginx/DirectoryStructure).

| Путь | Как его читать |
| --- | --- |
| `/etc/nginx/nginx.conf` | Главный файл: общие блоки и подключения |
| `/etc/nginx/conf.d/*.conf` | Дополнительные HTTP-настройки, если маска подключена внутри `http` |
| `/etc/nginx/sites-available/` | В схеме Ubuntu/Debian хранит конфигурации сайтов; наличие файла ещё не означает подключение |
| `/etc/nginx/sites-enabled/` | Обычно содержит символические ссылки на выбранные сайты и подключается отдельным `include` |
| `/etc/nginx/mime.types` | Соответствия расширений файлов и MIME-типов; это не конфигурация отдельного сайта |

Проверьте реальный `nginx.conf`: наличие каталога на диске не доказывает, что он подключён. Создание `sites-enabled` в установке из `nginx.org` само по себе не подключит сайты. В схеме с маской `sites-enabled/*` отсутствие расширения `.conf` не мешает чтению файла.

## 5. Посмотрите подключённые файлы через nginx -T

```sh
sudo /usr/sbin/nginx -T
```

`-T` выполняет проверку, как `-t`, и дополнительно печатает главный и подключённые файлы. При успехе среди диагностических сообщений будут строки:

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

Содержимое файлов начинается с отметок вида:

```text
# configuration file /etc/nginx/nginx.conf:
# configuration file /etc/nginx/mime.types:
# configuration file /etc/nginx/conf.d/default.conf:
```

Здесь приведены только отметки: в настоящем выводе за каждой идёт содержимое соответствующего файла. Список зависит от пакета и ваших настроек. Найдите блок `server` и ближайшую предшествующую отметку — она указывает файл, в котором он записан. Затем проследите `include`, чтобы определить контекст подключения.

`-T` читает текущие файлы с диска. Команда не выгружает конфигурацию из памяти работающего master-процесса и не применяет изменения: после редактирования её вывод может отличаться от настроек, с которыми служба продолжает работать. Также вывод сохраняет директивы `include`; это набор файлов с отметками, а не один готовый файл для замены `nginx.conf`. [Параметры командной строки](https://nginx.org/en/docs/switches.html), [формирование вывода в исходном коде](https://github.com/nginx/nginx/blob/master/src/core/nginx.c).

Вывод может содержать пароли и токены, записанные в директивах. Перед передачей фрагментов другим людям удалите такие значения.

## Какой файл редактировать

Для общих параметров процессов найдите соответствующие директивы в главном файле. Для настроек конкретного сайта найдите файл его `server` по выводу `-T`. Если он подключён через символическую ссылку в `sites-enabled`, проверьте её цель в `sites-available`.

Перед изменением запишите путь исходного файла и сделайте его резервную копию вне подключаемых масок. После правки проверьте конфигурацию:

```sh
sudo /usr/sbin/nginx -t
```

Проверка не применяет изменения. Порядок перечитывания конфигурации работающей службой описан в разделе [«Reload и restart»](./startup#reload-и-restart).

## Проверка результата

Итерация выполнена, если вы можете:

1. Назвать главный файл и объяснить, переопределён ли он параметрами службы.
2. Найти нужный `server` в выводе успешного `nginx -T` и назвать исходный файл.
3. Показать цепочку `include`, по которой этот файл читается внутри `http`.
4. Объяснить, какие файлы подходят под используемую маску и почему файл вне неё не подключён.

## Если что-то пошло не так

| Симптом | Что проверить |
| --- | --- |
| `directive is not allowed here` | Контекст директивы и место `include`; нет ли лишнего `http` вокруг файла с `server` |
| `unexpected "}"` или `unexpected end of file` | Парность скобок и `;` перед строкой ошибки; причина может быть выше указанной строки |
| `open() ... failed` | Путь из сообщения, права чтения и цель символической ссылки |
| Файл сайта отсутствует в `-T` | Главный файл, цепочку `include`, маску и расширение файла; сначала убедитесь, что проверка завершилась успешно |
| Файл есть в `-T`, но служба ведёт себя по-старому | Совпадают ли бинарный файл и параметры проверки со службой; применялись ли изменения после редактирования |
| Ошибка после добавления резервной копии | Не попала ли копия под `*.conf` или `sites-enabled/*`; одинаковые настройки могут подключиться повторно |

Начинайте с пути и номера строки в диагностике. При неуспешной проверке не считайте вывод `-T` полным списком подключённых файлов.
