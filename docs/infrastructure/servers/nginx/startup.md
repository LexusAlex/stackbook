# Запуск и автозагрузка

Запустим Nginx через systemd и настроим запуск при загрузке ОС. Проверяем два независимых результата: служба работает сейчас, а её запуск при загрузке включён.

## Перед началом

Нужен сервер Ubuntu или Debian с systemd, установленным пакетом Nginx и доступом к `sudo`. Проверка пакета описана в статье [«Установка Nginx»](./installation).

Используйте пакетную службу `nginx.service`. Запуск отдельной командой `sudo nginx` обходит управление службой; такой процесс не стоит смешивать с запуском через systemd.

## 1. Найдите службу

```sh
systemctl cat nginx.service --no-pager
```

Команда показывает unit-файл и его дополнения. В секции `[Service]` описаны команды запуска, остановки и перечитывания конфигурации; `[Install]` задаёт подключение к загрузке системы. Не создавайте второй unit, если пакетный уже есть. Формат описан в руководствах [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) и [systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html).

## 2. Проверьте конфигурацию и запустите Nginx

```sh
sudo /usr/sbin/nginx -t && sudo systemctl start nginx.service
```

Благодаря `&&` запуск выполнится только после успешной проверки конфигурации. `nginx -t` не запускает сервер; он проверяет синтаксис и доступность указанных в конфигурации файлов. [Параметры Nginx](https://nginx.org/en/docs/switches.html).

Посмотрите состояние:

```sh
LC_ALL=C systemctl status nginx.service --no-pager --full
systemctl is-active nginx.service
```

В `status` ожидается `Active: active (running)`, в ответе `is-active` — `active`. `Main PID` и дерево процессов помогают увидеть процессы этой службы. `LC_ALL=C` делает подписи в выводе англоязычными.

Если служба уже работает, `start` не перезапускает её. Описание запуска и проверки состояния: [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html).

### Что происходит при запуске

1. **systemd готовит запуск службы.** Использует загруженные настройки unit и его зависимостей, выполняет `ExecStartPre`, если он задан, затем `ExecStart`. Дополнительная проверка конфигурации в unit зависит от пакета: команда выше выполняет `nginx -t` явно.
2. **Nginx подготавливает рабочее окружение.** Читает `nginx.conf` и подключённые файлы, подготавливает журналы и слушающие сокеты. Ошибки конфигурации, доступа к файлам или открытия порта могут сорвать запуск.
3. **Появляются master и worker-процессы.** Master управляет конфигурацией и рабочими процессами. Worker-процессы принимают соединения и обрабатывают запросы; их число задаёт `worker_processes`.
4. **systemd отслеживает службу.** Правило завершения запуска задаётся `Type`. Например, при `Type=forking` systemd ждёт выхода начального процесса и определяет основной процесс, обычно по `PIDFile`.

Роли процессов описаны в [руководстве Nginx](https://nginx.org/en/docs/beginners_guide.html), этапы unit — в [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).

Упрощённая схема для обычного режима с master-процессом:

```text
systemctl start
      |
   systemd -- ExecStart --> master Nginx
                              |-- worker
                              `-- worker
```

Сверить настройки именно своей службы можно так:

```sh
systemctl show nginx.service -p Type -p PIDFile -p ExecStart -p ExecReload -p ExecStop -p KillSignal -p TimeoutStopUSec
```

Если `ExecStart` использует другой бинарный файл или параметр `-c` с нестандартной конфигурацией, команды проверки должны учитывать эти же пути. Статус `active` описывает состояние службы по правилам unit, а не результат HTTP-запроса к сайту.

## 3. Включите автозагрузку

```sh
sudo systemctl enable nginx.service
systemctl is-enabled nginx.service
```

Ожидаемый ответ — `enabled`. Постоянное включение опирается на секцию `[Install]` unit-файла и сохраняется между загрузками ОС. Значение `enabled-runtime` действует только до перезагрузки и не подходит для этой задачи. [Настройки установки unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#%5BInstall%5D%20Section%20Options).

**`start` и `enable` решают разные задачи:** первая команда запускает службу сейчас, вторая подключает её к загрузке системы. `enable` без дополнительных параметров не запускает остановленную службу.

Альтернатива раздельным `start` и `enable` после проверки конфигурации:

```sh
sudo systemctl enable --now nginx.service
```

Проверяйте оба состояния:

```sh
systemctl is-active nginx.service
systemctl is-enabled nginx.service
```

Нужны соответственно `active` и `enabled`. Варианты параметра `--now` описаны в [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html).

Автозагрузка и восстановление после аварии тоже различаются. `enabled` подключает службу к загрузке ОС; будет ли systemd перезапускать упавший Nginx, определяет отдельная настройка `Restart` в unit. [Политика перезапуска службы](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#Restart=).

## 4. Проверьте запуск после перезагрузки

Выполняйте проверку, когда перерыв в работе сервера допустим. Перезагрузка завершит текущие процессы и разорвёт SSH-соединение:

```sh
sudo systemctl reboot
```

Дождитесь загрузки сервера и подключитесь по SSH заново. Выполните:

```sh
systemctl is-enabled nginx.service
systemctl is-active nginx.service
sudo journalctl -b -u nginx.service -n 30 --no-pager
```

Ожидаются `enabled`, `active` и сообщения об успешном запуске в текущей загрузке. У `journalctl` параметр `-b` выбирает текущую загрузку, `-u` — службу, `-n 30` — последние 30 записей. [Параметры журнала](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html).

Одного `enabled` недостаточно: попытка запуска при загрузке может закончиться ошибкой. Активность службы также не подтверждает доступность сайта извне — это зависит от конфигурации и сети.

### Что происходит при перезагрузке сервера

Перезагрузка ОС — отдельная операция, затрагивающая все службы:

1. systemd останавливает службы по их правилам завершения. Соединения с сервером, включая SSH и подключения к Nginx, не сохраняются через перезагрузку.
2. После загрузки ядра и файловых систем systemd строит зависимости запуска служб. Автозагрузка Nginx подключает его unit к нужному target; фактический порядок определяется зависимостями.
3. Nginx запускается заново: получает новые процессы, читает конфигурацию и использует исполняемый файл с диска. Процессы и соединения из прежней загрузки не возобновляются.

Таким образом, проверка журнала с `-b` подтверждает события именно новой загрузки, а не успешный запуск до перезагрузки. Общая последовательность описана в [bootup](https://www.freedesktop.org/software/systemd/man/latest/bootup.html).

## Остановка и отключение автозагрузки

| Команда | Действие |
| --- | --- |
| `sudo systemctl stop nginx.service` | Остановить службу сейчас, сохранив настройку автозагрузки |
| `sudo systemctl disable nginx.service` | Отключить автозагрузку, оставив работающую службу |
| `sudo systemctl disable --now nginx.service` | Отключить автозагрузку и остановить службу |

Это разные действия. Отключение автозагрузки не запрещает ручной запуск или запуск по зависимости от другой службы. Такое различие отмечено и в [документации Ubuntu](https://documentation.ubuntu.com/security/common-mistakes/unnecessarily-open-ports/).

## Reload и restart

### Разница в одной таблице

Сравнение относится к обычной пакетной службе Nginx с master-процессом и стандартным обработчиком reload:

| Что меняется | `reload` | `restart` |
| --- | --- | --- |
| Master-процесс | Продолжает работать, его PID сохраняется | Завершается; при успешном запуске создаётся новый |
| Worker-процессы | Новые запускаются, старые завершают текущую работу | Старые останавливаются, затем создаются новые |
| Обслуживание клиентов | Рассчитано на плавную смену конфигурации | Возможны разрыв соединений и пауза в приёме запросов |
| Ошибка при применении конфигурации | Master сохраняет прежнюю рабочую конфигурацию | Если новый запуск не удался, служба может остаться остановленной |
| Обновлённый бинарный файл Nginx | Работающий master не заменяется | Новый запуск использует файл с диска |
| Остановленная служба | Не запускается | Запускается, если проверка и запуск успешны |
| Настройка автозагрузки | Не меняется | Не меняется |

Перечитывание описано в [руководстве Nginx](https://nginx.org/en/docs/beginners_guide.html#control), операции службы — в [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html).

### Что происходит при reload

```sh
sudo /usr/sbin/nginx -t && sudo systemctl reload nginx.service
```

1. systemd вызывает обработчик `ExecReload`. В обычной службе Nginx он передаёт master-процессу сигнал `HUP` для перечитывания конфигурации.
2. Работающий master читает конфигурацию и пробует подготовить необходимые ресурсы, включая новые журналы и слушающие сокеты.
3. При успехе запускает новые worker-процессы. Старые перестают принимать новые соединения и завершают обслуживание текущих клиентов.
4. Если новую конфигурацию применить не удалось, master продолжает работу с прежней конфигурацией и процессами.

Это поведение самого Nginx описано в [Controlling nginx](https://nginx.org/en/docs/control.html#reconfiguration). Конкретную команду отправки сигнала проверяйте в своём unit.

Условный пример; буквы обозначают PID, а не реальные номера процессов:

```text
До reload:      master A --> workers B, C  (прежние правила)

После reload:   master A --> workers D, E  (новые правила)
                        --> workers B, C  (завершают текущие запросы)
```

Текущий запрос не переносится из старого worker в новый. Поэтому некоторое время могут сосуществовать поколения рабочих процессов с разными конфигурациями.

Долгие запросы и соединения, например WebSocket, могут задерживать завершение старых workers. Если задан `worker_shutdown_timeout`, после его истечения Nginx пытается закрыть оставшиеся соединения. Поэтому reload не даёт безусловной гарантии сохранения любого соединения. [Таймаут завершения workers](https://nginx.org/en/docs/ngx_core_module.html#worker_shutdown_timeout).

### Что происходит при restart

```sh
sudo /usr/sbin/nginx -t && sudo systemctl restart nginx.service
```

systemd выполняет остановку, затем новый запуск службы. Способ завершения определяется `ExecStop`, сигналами, `KillMode` и таймаутом остановки. Nginx различает мягкое завершение `QUIT` и быстрое `TERM`; нельзя считать любой `systemctl restart` безусловно мягким завершением. При исчерпании времени остановки systemd может принудительно завершить процессы. См. [правила завершения systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html) и [сигналы Nginx](https://docs.nginx.com/nginx/admin-guide/basic-functionality/runtime-control/#control-nginx-with-signals).

После остановки создаётся новый master с новыми workers. Существующие соединения не передаются новым процессам; во время смены возможен перерыв в обслуживании. Если запуск закончился ошибкой, прежний master уже не сможет продолжить работу. Предварительный `nginx -t` снижает риск, но не гарантирует успешный запуск в изменившихся условиях.

### Какую команду выбирать

| Изменение или задача | Действие |
| --- | --- |
| Изменили обычные настройки в `nginx.conf` или подключённых файлах | Проверить конфигурацию и выполнить `reload` |
| Нужно запустить остановленную службу | Выполнить `start` после проверки конфигурации |
| Нужно запустить заменённый бинарный файл Nginx | Использовать обычный перезапуск службы; reload работающий master не заменит |
| Изменили unit или его дополнения, например `ExecStart` | Выполнить `daemon-reload`, затем перезапустить службу для запуска с новыми параметрами |

У Nginx есть отдельная [процедура обновления бинарного файла на лету](https://nginx.org/en/docs/control.html#upgrade). Она не равнозначна обычному `reload`.

После изменения unit последовательность выглядит так:

```sh
sudo systemctl daemon-reload
sudo /usr/sbin/nginx -t && sudo systemctl restart nginx.service
```

`daemon-reload` перечитывает unit-файлы и зависимости для systemd. Он сам не перезапускает Nginx и не применяет `nginx.conf`. [Описание systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html).

### Как увидеть результат

Выполните эти команды до и после выбранной операции на учебном сервере:

```sh
systemctl show nginx.service -p MainPID --value
ps -C nginx -o pid,ppid,args
```

При обычном reload основной PID сохраняется, а PID workers меняются; старые workers могут ещё присутствовать с пометкой о завершении. После успешного restart создаётся новый master. Роли master и workers описаны в [документации NGINX](https://docs.nginx.com/nginx/admin-guide/basic-functionality/runtime-control/#master-and-worker-processes).

Если `ExecReload` только отправляет сигнал, успешное завершение команды ещё не подтверждает, что Nginx уже применил настройки: обработка сигнала асинхронна. Проверьте журнал, настроенный `error_log` и поведение изменённого сайта. Для стандартного пути журнала:

```sh
sudo journalctl -u nginx.service --since '-5 minutes' --no-pager
sudo tail -n 50 /var/log/nginx/error.log
```

Ограничения асинхронного `ExecReload` описаны в [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExecReload=). Отсутствие новых ошибок само по себе не подтверждает нужный HTTP-ответ: проверьте конкретное поведение, ради которого меняли конфигурацию.

## Если служба не запускается

Начните с подробного состояния, журнала текущей загрузки и проверки конфигурации:

```sh
LC_ALL=C systemctl status nginx.service --no-pager --full
sudo journalctl -b -u nginx.service -n 50 --no-pager
sudo /usr/sbin/nginx -t
```

`status` и `is-active` возвращают ненулевой код для неработающей службы. Это результат проверки, а не ошибка синтаксиса команды.

| Сообщение или состояние | Что проверить |
| --- | --- |
| `Unit nginx.service could not be found` | Установлен ли пакет на этом сервере и содержит ли он unit-файл |
| `failed` или сообщение об ошибке запуска | Первую содержательную ошибку в журнале; затем исправьте причину и повторите запуск |
| Ошибка конфигурации или отсутствующий файл | Путь и номер строки из `nginx -t`, наличие файлов и права доступа |
| `Address already in use` | Какой процесс занял нужный порт; список слушающих TCP-сокетов показывает `sudo ss -ltnp` |
| `masked` | Почему запуск службы был явно заблокирован; обычный `enable` эту блокировку не снимает |
| `System has not been booted with systemd` | Является ли systemd менеджером системы; эти команды не подходят для окружения с другим менеджером |

После исправления повторите запуск и обе проверки: `is-active` и `is-enabled`. При необходимости смотрите журнал с большим числом записей: последние 50 строк могут не содержать начало ошибки.
